Tab order and hidden views are saved in settings.json for this PC. Windows on disconnected screens are moved onto an available monitor. Theme, tab order, hidden tabs and zoom are remembered too. Closing a detached window manually still returns its tab to the main window. While you drag, neighboring tabs slide aside to preview where the tab will land. Release to place it, or press Escape to cancel. Releasing outside the tab strip detaches the view. Release to open a separate window, then move it to another monitor. Drag the detached header back to reattach it, or close its window. Returning to the tab bar or pressing Escape before release cancels detachment. Windows Snap Layouts arrange the main and detached windows without overlap. Licensing, activation and license expiry
Owner-issued licenses may be provided to partners, for evaluation, or under a separate commercial agreement. Activating a key does not make a payment or start an automatically renewing subscription. Any fees, license duration and support terms are agreed separately with the owner before obtaining a license. Help > License activation shows Free or Licensed and the UTC license end date. Free includes local-server synchronization. A license unlocks project name/logo/startup branding, cloud synchronization and encryption of new data. Name and surname are mandatory. Enter both, then Generate license request. An installed, verified machine-bound license supplies this identity automatically when saving revision history, including after license expiry. An application without a verified license still asks for editor details. The application combines them with this Windows installation's machine identity, a unique request ID and verified HTTPS time, and encrypts the request with the owner's public request key. Copy request and contact the project owner through Project support page; no request or payment is sent automatically. The owner decrypts the request in the separate ELMA-IoT MIE Keygen, chooses an expiry date and returns a signed unlock key. Paste it into the input and click Unlock, or Load product key from a .mielicense file. Either method activates a valid key, closes the activation form and shows a personalized congratulations window with remaining time. Close it using the window cross. The generated request appears automatically; Copy request copies it. The app checks the owner signature, product, machine identity, trusted time and expiry. A reusable plain-text .mielicense backup is kept in Keys beside the portable EXE, or the Store edition's writable application data folder. Application updates keep these local files. If the protected license state is missing, a matching saved product key can be loaded again; a product key for another Windows installation is rejected. About and Help show edition and license end. The bottom of About centers the licensed name and surname above a live remaining-time countdown. Unverified internet time is reported instead of an estimated countdown. After expiry, Free remains usable, cloud sync and new encryption are unavailable, and standard branding is displayed. Imported data, saved custom branding and existing encrypted files are retained. Keep encryption keys separate from product unlock keys. The owner keygen is private administration software and is not included in customer project ZIP exports. An unreadable, unrecognized, invalid or wrong-PC license file beside the EXE produces a startup notice on each launch until removed or replaced. OK keeps the application open in free mode when no valid license is active; a rejected portable file cannot activate paid features through a cached license.

License time and clock protection
licensed features require a fresh HTTPS time check on each application start. The check reads time headers from Microsoft and Google without sending names, machine IDs or project data to those sites. Two available responses must agree within five minutes; if only one succeeds it is used. Invalid responses, blocked HTTPS or certificate failures leave Licensed unavailable until a successful Recheck license time. After verification, Windows' monotonic uptime counter advances license time through sleep and hibernation, independently of the editable calendar clock. An open session retries time checks hourly and permits at most twenty-four hours without a new successful check. Moving Windows time backward does not extend the license. A protected high-water time record also rejects stale responses. Expiry is checked during use and before licensed operations; files already being committed finish safely. No desktop-only license scheme can fully resist an administrator patching the executable, stealing owner keys or restoring an entire virtual machine snapshot. A future account website can add signed server leases, revocation and balance billing. The current owner keygen already records request creation, owner receipt and license issue/expiry as JSONL for that integration. Keep the owner signing and request-decryption keys private and export their password-encrypted backup from the keygen before moving to another PC.

Optional project and backup encryption
Compression and encryption are separate options. Compression-only projects, incremental batches, commit indexes and snapshots are ZIP archives and need no key. They still validate file hashes and snapshot/event coverage. If encryption is enabled with a matching key and the existing encryption license, new shared objects use the existing authenticated MIEENC1 format. Every authorized PC needs the original project key to open an encrypted backup folder; keep its .miekey backup private. The app does not automatically remove encryption from an existing encrypted shared folder. Original legacy backups are never overwritten or encrypted in place. Existing encrypted local working projects, journals and recovery backups retain their encryption even when shared synchronization is compression-only. Data is held in RAM while open. This upgrade adds no database dependency or local-storage migration.

Project synchronization
After explicit pairing, MIE synchronizes automatically every minute when enabled. The server remains passive file storage. New shared writes use compressed immutable transaction batches in MIE_Backup/changes, complete snapshots in snapshots, and retained recovery material in archive. Encryption is optional; compression-only folder sync does not require a project key or encryption license. A conditional commit index defines causal order. Unreferenced or partially uploaded files are never committed. Clients use a local checkpoint and download only missing batches without scanning the entire history. An unchanged sync does not rewrite the local project or create a full local backup. Transactions retain stable record IDs, previous and new values, original available authors, UTC times and causal revision references. Unknown authors remain Unknown. The existing three-way merge combines independent fields and separate PN/SN edits automatically. Genuine conflicts open field review and resolution creates a new audit event; Resolve later preserves pending work. Equipment assignment conflicts and complex simultaneous workbook layout or dictionary changes may require reconciliation. Original legacy single-project backups remain readable and are never overwritten by updated clients. Check legacy backup is off by default in Sync settings. Only when it is enabled does the client read and reconcile the legacy single-file backup against its imported ancestor; identical imports are deduplicated. When off, legacy metadata and content are not read on local, network or supported cloud destinations. A complete copied backup folder restores offline through File > Import > Import / Restore backup folder. Restore as new project chooses a destination; Merge into current project reviews conflicts and backs up current work. Required hashes, project identity, exact snapshot event coverage and native workbook/drawing resources are checked before saving. A damaged latest snapshot can fall back to an earlier valid snapshot and replay retained batches only when the exact current state can be reconstructed. Required missing data stops recovery. History is never automatically deleted. Local storage, in-memory navigation and the existing native-part recovery journal remain unchanged; existing local encryption is preserved even when shared sync uses compression only. Save a new project first so its journal has a file location. Sync and backup processing run on background workers without a database migration.

Set up server and cloud connections
Choose a network share or supported cloud provider, a shared project filename and a unique PC alias. Folder and WebDAV destinations use a dedicated backup folder derived from the filename, such as MIE_Backup. Compression-only synchronization works without a key; leave encryption disabled to use it. Optional encryption of new shared files uses the existing encryption license and the same project key on authorized PCs. Cloud providers still require the cloud license. Do not replace the key of an existing encrypted backup folder; use its original key. Existing encrypted local projects and recovery backups keep their encryption even when the shared folder is compression-only. Snapshot defaults are 100 committed batches or 24 hours when changes exist; both thresholds are configurable. Test the connection to verify exclusive locking, immutable creation and conditional replacement. Google Drive requires the exact shared backup-folder ID because names are not unique. Create Google backup folder creates a dedicated folder; grant each authorized Google account Editor access and use the same folder ID on every PC. The existing legacy Google project-file ID is optional and read-only during migration. OAuth credentials alone do not grant folder access. Progress records requests, elapsed waiting and cancellation in one window. Failure or cancellation exposes Retry after the worker stops. An administrator may clear a stale cloud lease only after verifying its owner has stopped. Check legacy backup is off by default. When it is off, synchronization does not read, hash or reconcile the old single-file backup on folder, network or cloud storage. Turn it on only when you want read-only reconciliation of that legacy file. The setting is saved per installation and applies to manual and automatic sync. Incremental changes, snapshots, local recovery and encryption settings continue to work independently.

Sync backups, rollback and audit
Local UTC-dated backups retain application version information and revision history. Restoring a local backup creates a recovery copy first and requires explicit sync before sharing restored changes. Copy the entire MIE_Backup folder, including head.mieindex, changes, snapshots and archive, to move a shared backup to another PC. Choose File > Import > Import / Restore backup folder, select the copied folder, and choose Restore as new project or Merge into current project. A compression-only folder needs no password. Enter its original project key only if it is encrypted. Validation checks file integrity, project identity, exact snapshot event coverage, causal order and native resources. New-project restoration asks for a destination. Merge preserves current work and prompts for genuine conflicts. Missing required batches cannot be skipped; unreferenced and partial .writing uploads are ignored. Keep historical files until a separately verified retention mechanism is available. Known legacy shared files and incremental backup objects are read-only in MIE. Use Save as… for a separate working copy.

Replenishment policy and forecast quality
Select a policy row and open Policy. Set target stock, safety stock, manual weekly demand, planned campaign demand, forecast period and forecast mode. Physical minimum is a stock threshold. Reorder point is the greater of that minimum and safety stock plus expected demand during lead time plus planned demand. Safety stock defaults to the minimum, so the same buffer is not added twice. Suggested order quantity considers available stock, timely dated incoming orders, the reorder point and target stock. Undated, overdue or too-late orders stay on order but are not credited as timely replenishment. Planned demand is treated as already allocated; do not include it twice. Manual or Campaign planning is preferred for irregular drilling demand. History forecasting is opt-in, uses weighted 30, 90 and 180-day net consumption and requires at least three consumption dates spanning 30 days. Returns net against matching prior well and serial consumption. Transfers, reservations, receipts and adjustments are not consumption. Without adequate history, the application states Insufficient consumption history. Dated incoming orders are applied to projected stock; a forecast stockout before delivery is critical. Red means critical shortage or timing risk, yellow means action or partial coverage, blue means a physical shortage covered by dated incoming orders, and green means the configured policy is met.

Autofill — automatic forecast and data checks
Autofill is the table-with-sparkle icon immediately left of Edit in the licensed Min. Stock header. It moves with the tab when detached. The button is disabled when no supported forecast can be calculated; hover it to see what is missing. Manual stock-policy editing remains available. The readiness check is cached and refreshed after relevant project changes and at date/language refresh; it does not save project data.
Autofill can use an approved dated equipment requirement in the active schedule scenario, or a dated upcoming drilling activity plus sufficient historical installation evidence. An approved requirement needs a valid PN, a positive quantity and a readiness date that is not in the past. Proposed or rejected requirements are not accepted as confirmed demand. Cancelled, completed, postponed and summary activities are excluded.
For historical estimates, eligible reference wells are distinct named wells with valid spud and end dates, an end date on or before today, and an end date no earlier than spud. At least three distinct completed wells must span 30 days by spud date. Each suggested historical PN also needs at least three positive examples spanning 30 days. These are minimum evidence checks, not a guarantee of statistical reliability. A blank or unverified equipment slot is excluded rather than counted as zero demand. Operational dates estimate consumption timing; they are not actual stock-movement timestamps.
The default opens and calculates automatically using eligible history and the current rig schedule. No manual well selection is required. Use selected historical wells only is an optional override; the same sufficiency checks apply to the selected subset. Change forecast start or the 1–520 week horizon, then Analyze references to recalculate. The default horizon is 52 weeks. The tool uses the active schedule scenario. A period with no supported demand shows an explanation rather than invented recommendations.
Historical PN mix is calculated within each standard equipment slot from positive verified PN records. A PN observed on 6 of 10 positive slot records contributes an estimated 0.6 units per future drilling well, not one unit on every well. Different variants are therefore not all assumed to be installed on each future well. PNs below the minimum evidence threshold are omitted without redistributing their share. If a scheduled region is specified, only matching historical region records are used; recognized Black Sea and Mediterranean names are normalized. If region/design is unspecified, pooled historical PN mix is labeled lower-confidence and requires an applicability review. Historic designs are not inferred from filenames or serial numbers.
Only included dated drilling activities contribute to historical estimates. Completion, rig moves and maintenance do not automatically consume drilling hardware. A repeated named planned well is counted once. Explicit approved equipment requirements take precedence for an activity; historical estimates are not added to the same activity, so partial approved plans still require a completeness review. The Approved schedule requirements mode restricts the calculation to explicit approved demand. Exact, month and quarter schedule dates retain their stored precision; earliest plausible starts are used for conservative timing.
For permanent equipment, expected quantities are grouped by PN and projected onto schedule dates. The recommendation is the ceiling of peak demand within a replenishment window plus configured safety stock. A known requirement/policy lead time defines the window; the largest known lead time for that PN is used. If no lead time is known, the selected forecast horizon is explicitly used as a planning assumption; supplier lead time is left unfilled. Reusable equipment uses peak concurrent units between planned start and finish, not permanent consumption. Without a finish date its occupancy is held indefinitely. Mixed reusable/permanent classification and duplicate policies for one PN are omitted for manual resolution.
The preview shows current minimum, recommendation, editable proposed minimum, lead time and evidence. Hover a row to read the calculation. Automatic historical estimates are unchecked by default; tick Apply only for reviewed rows. Existing higher manual minima are preserved by default. Current stock and open orders are not subtracted from a minimum physical-stock threshold. Use the separate schedule procurement view for dated stock allocation and proposed order quantities; an Autofill threshold is not itself an order quantity.
Apply changes only selected stock policies, fills unknown policy lead time only when supported, and can add missing PN policies. It does not approve schedule BOM items, place orders, assign serial numbers, record receipts or consume inventory. One Undo reverses the batch; Redo restores it. Normal named revision history records the changes. Native policy values and supporting revision history survive project save, synchronization and licensed Excel export. A manually entered minimum below the last reviewed recommendation glows with a hover explanation. That warning refers to the last reviewed calculation; rerun Autofill when history, programme or assumptions change.
The current Autofill is an explainable schedule and historical-installation-mix estimator. It does not fit a continuous monthly consumption rate, automatically infer well-design applicability, calculate shortage probabilities or automatically learn supplier reliability. Actual consumption movement forecasting in the separate policy engine has its own data requirements. A sufficient-evidence flag permits a reviewable estimate; it does not imply that a forecast is factual or high-confidence. The guide tutorial demonstrates insufficient and sufficient data using a temporary synthetic project, calculates a preview and applies a demonstration value, then restores the original workspace without saving its data. Apply checkboxes are centered and toggle with one click. Click the Apply column header to select every proposal, then click again to clear all; a mixed selection selects all on the next header click.

Condition, availability, disposition and location
Condition describes the equipment: Serviceable, Suspected Damage, Damaged, Failed Inspection, Awaiting Assessment or Beyond Economical Repair. Use controlled lifecycle actions to change these fields; ordinary cell edits cannot replace the Equipment ID or bypass lifecycle state controls. Existing ordinary data corrections, custom fields and formatting remain possible for active records, and are recorded. A stable Equipment ID travels with transfers. Serialized equipment represents one physical unit. A partial quantity action on nonserialized stock creates a new child Equipment ID with Parent Equipment ID, reduces the original quantity and preserves metadata. The confirmation displays the action, unit, quantity, actual date/location, application user, approver and evidence. Its Confirm action button remains disabled until the explicit confirmation checkbox is selected. Cancel records no approval.
The existing license holder name and license user ID are captured automatically when present. They identify the application user, not verified authorization or a currently authenticated operator. The separately entered approver identity is self-declared. When there is no license identity, the workflow captures the declared name and identity source. Approval records include UTC confirmation and recorded timestamps and an extensible approval context. No new roles, Windows-account restrictions, authentication, licensing rules, KeyGen changes or Superadmin changes are introduced. RBAC is deferred to a future major release without requiring a different historical approval record format.
A document reference is allowed when a file is not attached. Embedded files are content-hashed and travel with native project saves and applicable exchanges; History can save an evidence copy. References are declarations, and the application does not verify that an external report proves the engineering condition. App history is read-only through normal controls and detects inconsistent event hashes; users with external file/system access are not prevented by a claimed tamper-proof signature scheme. Offline approvals remain supported.

Inspection, repair, testing and release
Send to Quarantine records the condition and reason while retaining the owned physical item. Inspection and testing are applicable by default. If testing is genuinely not applicable, document the exemption justification when quarantining; this is a recorded declaration, not an automatic engineering assessment. Record Inspection records Pass or Fail with evidence. Failed inspection keeps the item unavailable. A new inspection resets test readiness so an old test is not silently reused.
Send for Repair requires the actual facility location and supporting reference. It sets offsite custody and Repair / Rework, removes it from physically held/available stock and retains ownership. Record Repair Completion records evidence, actual location and whether it remains offsite or is physically returned; it does not automatically release the item. Inspection and applicable test/certification results must then be recorded. A failed test keeps the equipment unavailable.
Release to Service requires a passed inspection, applicable passed test or documented exemption, completed repair where required, named confirmation, evidence and an actual service location. Equipment still offsite must be explicitly recorded as physically returned. BER equipment needs a new assessment before release. Successful release transfers the same identity back to Inventory with serviceable/available state. It cannot bypass the engineering evidence checks by ordinary cell editing. Stock calculations and Outstanding update after the transaction.

BER, scrap approval and completed disposal
Declare Beyond Economical Repair records the assessment and evidence while leaving the owned item unavailable. Approve for Scrap is a separate named approval; it does not mean the equipment has physically left the stock location and does not reduce physically held stock. The item remains in Quarantine with Approved for Scrap disposition until disposal is actually completed.
Complete Disposal requires the separate scrap-approved predecessor, a reason, evidence/reference and a dedicated named confirmation. It removes only the completed quantity from active physical/available/incoming stock and retains PN, SN, location, documents and lifecycle events. A partial nonserialized disposal splits a child identity, leaving the remaining quantity intact. The disposed item moves out of the active Quarantine view into Disposed archive, which is audit-only.
Ordinary edits, transfers and Undo cannot make a disposed item available again. Use a documented Reverse Disposal action with confirmation and evidence if a disposal was recorded incorrectly. It preserves the original disposal and returns only to unavailable Pending Assessment; it does not skip inspection/testing or release approval. The reversal itself is also protected from ordinary Undo. Source records and histories are preserved rather than overwritten. This workflow records declared approvals; it does not implement future RBAC or verify external physical-disposal evidence.

Lifecycle sync, backups and exchanges
Lifecycle metadata and supporting documents use the existing compressed native project resources, optional encryption, recovery journals and incremental shared-file synchronization. No database server or new local database is introduced. Independent equipment histories can merge; conflicting offline lifecycle states require an explicit reviewed choice, retaining both histories and a resolution record. An available choice cannot overwrite completed disposal; select the disposed state and use a documented reversal if appropriate. Cancelling conflict review preserves both copies.
Known disposal history is reconciled before accepting older active stock through supported sync and MIE-pack exchange. A Windows-user-protected local disposal safeguard also retains known terminal history and evidence for that project when older local backups are opened. It is scoped to the local account and known project; a completely disconnected PC with only an old file cannot know about disposal information it has never received. Synchronize or open a current project before relying on its availability. No global server authority or tamper-proof database is claimed.
Single-record MIE packs retain the selected equipment identity, relevant history and evidence and exclude unrelated records. They have their own project/sync identity, so a local safeguard cannot inject another project's unrelated disposal history. Existing keys and licensing are unchanged. Full native project files remain the preferred lifecycle backups.
Excel export includes an Equipment Lifecycle audit worksheet, canonical event records and supporting resources by default. The audit sheet is protected for normal editing, with a hidden canonical record column for reimport. Condition/availability fields are separate from PN/SN and location. Excluding the lifecycle sheet also excludes its evidence payload; a selective spreadsheet is not a complete lifecycle backup. Imported disposal status without original events is kept unavailable for evidence review. The old Scrap label alone is never treated as completed disposal.

Physical stock, availability and procurement
Physically held stock is serviceable held stock plus quarantined held stock. Available stock is eligible serviceable Inventory minus recorded reservations. Quarantined stock remains physically held but unavailable. Offsite repair stock remains owned at its external location and is reported separately from physically held stock. Disposed quantities are historical only. Installed well equipment is allocated/historical equipment and is not available warehouse stock.
Only confirmed outstanding In-Order quantities contribute incoming supply; fully received, cancelled, explicitly draft/proposed or rejected orders do not. Quarantine never becomes an incoming order. Stock forecasts, minimum-stock coverage and recommendations use eligible available stock, not all owned stock. Transfers, reservations, repair and disposal are not fabricated well-consumption events. Existing historical/schedule forecast assumptions remain unchanged.
Serialized duplicates are counted at most once and kept unavailable pending review, rather than inflating coverage. Repeated PNs with distinct SNs remain valid. Stable IDs and quantity splits preserve total balances across transfers, partial quarantine, repair, release and disposal. Outstanding records assessment, offsite repair, scrap/disposal and stale-restoration actions. Licensed Metrics adds physical held, available, quarantined, offsite owned and disposed-history counts plus numeric per-PN Excel data. Min. Stock, Forecasting and Metrics remain licensed; the core Inventory/Quarantine lifecycle remains available in the free workflow.
